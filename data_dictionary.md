## 1. `customers.csv`

**Format:** CSV (comma-separated, header row present)
**Row count:** 1,500 (plus header)
**Customer IDs observed:** 1–1,500 (contiguous, no gaps observed)

### Schema

| Column | Dtype | Nullable (observed) | Description |
|---|---|---|---|
| `customer_id` | int64 | No | Unique customer identifier. Sequential integer, 1–1,500. |
| `signup_date` | object (date) | No | Date the customer signed up/registered. Format YYYY-MM-DD. Range: 2024-02-14 to 2026-07-01. |
| `acquisition_channel` | object (categorical) | No | Channel through which the customer was acquired. Values observed: `organic`, `paid_search`, `social`, `referral`. |
| `region` | object (categorical) | No | Geographic region of the customer. Values observed: `east`, `west`, `north`, `south`. |
| `churned` | int64 (0/1) | No | Binary churn label. 1 = churned, 0 = active/not churned. |

### Observed value distributions

- **Churned:** Manual spot-check shows a mix of 0 and 1 values.
- **Acquisition channels:** Four distinct channels: `organic` (appears most frequent), `paid_search`, `social`, `referral`.
- **Regions:** Four regions: `east`, `west`, `north`, `south`.

### Data-quality notes

- No null values detected in any column across the visible rows.
- `customer_id` is a contiguous integer sequence with no gaps.
- The `churned` label is defined at the customer level and is not time-varying. A customer is either churned or not; there is no churn _date_ column, only a point-in-time binary flag.

## 2. `transactions.db` (SQLite)

**Format:** SQLite 3.x database, single table (`transactions`)
**Row count:** 11,742 rows
**Distinct customers:** 1,419

### Schema

| Column | Dtype | Nullable (observed) | Description |
|---|---|---|---|
| `customer_id` | INTEGER | No (0 nulls) | Foreign key to `customers.csv`. 81 customers from the CSV have zero transaction rows here. |
| `txn_timestamp` | TEXT | No (0 nulls) | Transaction timestamp. Format: ISO-8601 string. |
| `category` | TEXT | No (0 nulls) | Product/service category of the transaction. |
| `channel` | TEXT | No (0 nulls) | Transaction channel (e.g., `web`, `mobile`, `in_store`). |
| `amount` | REAL | No (0 nulls) | Monetary value of the transaction. Strictly positive (Minimum: 3.0, Maximum: 1684.21). |
| `is_returned` | INTEGER (0/1) | No (0 nulls) | Whether this transaction was a return. 1 = returned, 0 = not a return. |

### Time dimensions

- **Grain:** Individual transaction (row-level). Each row is one transaction event.
- **Timestamp column:** `txn_timestamp` (TEXT, ISO-8601).
- **Temporal range:** 2024-02-29 18:44:13 to 2026-07-31 23:50:29.

### Data-quality notes

- **Zero-transaction customers:** Exactly 81 customers present in `customers.csv` have no records in this database. 
- **Return Mechanics:** There are no negative amounts in the dataset. Returns are captured strictly via the `is_returned = 1` flag on rows with positive amounts (591 returned rows observed). 
- **Nulls:** Zero nulls exist across all columns.

## 3. `transactions_monthly_agg.parquet`

**Format:** Apache Parquet
**Row count:** 8,086 rows
**Distinct customers:** 1,409

### Schema

| Column | Dtype | Nullable (observed) | Description |
|---|---|---|---|
| `customer_id` | int64 | No (0 nulls) | Foreign key to `customers.csv` / `transactions.customer_id`. |
| `txn_month` | datetime64[us] | No (0 nulls) | 1st of the month boundary timestamp (e.g., 2024-09-01 00:00:00). |
| `txn_count` | int64 | No (0 nulls) | Total transaction count for this customer in this month. |
| `total_amount` | float64 | No (0 nulls) | Sum of transaction amounts for this customer in this month. |
| `return_count` | int64 | No (0 nulls) | Number of returned items (`is_returned=1`) in this month. |

### Time dimensions

- **Grain:** Customer-month. One row per customer per calendar month.
- **Month column:** `txn_month` — standardizes to the 1st of each calendar month.

### Data-quality notes

- **Customer Discrepancy:** 10 customers who exist in `transactions.db` are completely missing from this Parquet aggregate. Downstream loaders must account for this when joining data.
- **Nulls:** Zero nulls exist across all columns.
- The parquet format preserves `datetime64[us]` and `int64`/`float64` types precisely.

## 4. Cross-Source Data-Quality Realities

### Source coverage overlap

- **Total Base Customers:** 1,500 (`customers.csv`).
- **Customers in DB:** 1,419.
- **Customers in Parquet:** 1,409.
- **Zero-activity customers:** 81 customers appear in `customers.csv` but in neither transaction source. Every feature that derives from transaction data must have an explicit default for these customers (e.g., `0` for counts, `0.0` for spend, and a sentinel like `-1.0` for recency).
- **Discrepancy at the margins:** 10 customers are present in the DB but missing from the Parquet roll-up. Features built from short trailing windows should prefer the row-level SQLite database to avoid missing recent activity.

### Temporal coverage

- Base customer signup dates range from **2024-02-14 to 2026-07-01**.
- Transaction activity ranges from **2024-02-29 to 2026-07-31**.

# Candidate-Feature Proposal

> **Status: Verified Proposal.** These features are mapped directly to the confirmed ground truth of the dataset.

Each block below follows the format: **name** | **source(s)** | **computation** | **zero-activity default** | **rationale** 

---

### F1: `days_since_last_txn`

- **Source:** `transactions.db` 
- **Computation:** `as_of - max(txn_timestamp)` per customer from transactions.db, clipped at `as_of`.
- **Zero-activity default:** `-1.0` (A sentinel value to clearly separate "never transacted" from "transacted long ago").
- **Rationale:** A customer who hasn't transacted recently is signaling active disengagement. This recency signal is distinct from low frequency because a high-frequency buyer can still abruptly stop.

---

### F2: `txn_count_90d`

- **Source:** `transactions.db` 
- **Computation:** `COUNT(*)` for each customer where `txn_timestamp > as_of - 90d`.
- **Zero-activity default:** `0`
- **Rationale:** A drop in recent transaction count is a preceding churn signal. Distinct from recency: someone can have transacted recently but only once, which is a different behavioral pattern.

---

### F3: `recent_net_spend_90d`

- **Source:** `transactions.db` 
- **Computation:** `SUM(amount * (1 - is_returned))` per customer where `txn_timestamp > as_of - 90d`.
- **Zero-activity default:** `0.0`
- **Rationale:** Decreasing net spend in recent months is a direct churn signal. Calculating net spend is required because returns hold positive `amount` values in the raw data.

---

### F4: `avg_monthly_spend_6m`

- **Source:** `transactions_monthly_agg.parquet` 
- **Computation:** Average of `total_amount` over the trailing 6 months (the 6 latest `txn_month` rows per customer) up to the `as_of` date.
- **Zero-activity default:** `0.0`
- **Rationale:** A customer's typical spend level establishes a baseline. A recent drop means more if the customer was historically high-spending compared to someone who was always low-spending.

---

### F5: `active_months_12m`

- **Source:** `transactions_monthly_agg.parquet` 
- **Computation:** Count of distinct months in the trailing 12 months where `txn_count > 0`.
- **Zero-activity default:** `0`
- **Rationale:** Consistency of engagement over a longer window highlights habitual users. Someone active in 11 of 12 months is structurally more engaged than someone active in only 2 months.

---

### F6: `lifetime_return_rate`

- **Source:** `transactions_monthly_agg.parquet`
- **Computation:** `SUM(return_count) / SUM(txn_count)` per customer across all historical months.
- **Zero-activity default:** `0.0`
- **Rationale:** A high return rate is a classic proxy for dissatisfaction. Customers frustrated with product quality are highly likely to churn, even if their gross spend remains high temporarily.

---

### F7: `tenure_days`

- **Source:** `customers.csv` only
- **Computation:** `as_of - signup_date`
- **Zero-activity default:** N/A (All customers have a signup date).
- **Rationale:** Tenure normalizes other behavioral counts. Low transaction counts are expected for a 10-day tenure customer, but alarming for a 300-day tenure customer.

---

### F8: `acquisition_channel` and `region` (static features)

- **Source:** `customers.csv`
- **Computation:** Direct passthrough (categorical). 
- **Zero-activity default:** N/A (All customers have these values).
- **Rationale:** Baseline customer profile attributes. Certain acquisition channels (e.g., social) may historically carry a higher baseline churn probability than others (e.g., referrals).
